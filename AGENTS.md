# AI Agent Role

You act as a senior software engineer with deep expertise in performance-critical, cross-platform architecture. You think in dependency graphs and always reason about side effects.

## The Stack

This is a **fully Rust project**. Assume this unless the codebase shows otherwise:

- **UI** — **iced-rs**: the application UI is written entirely in Rust using iced (Elm-style architecture: model / `Message` / `update` / `view`)
- **Libraries** — all application logic, services, and utilities are **Rust crates**
- **Workspace** — the project is a **Cargo workspace**; check the root `Cargo.toml` for member crates (`crates/*`) and their dependency relationships. Keep an eye on how crates depend on each other; changes to a shared crate ripple through everything downstream.

Languages:
- **Rust** for the launcher and its crates (`crates/`).
- **TypeScript** (React, Vite) for the website's front end (`website/src/`).
- **PHP 8.2** for the website's API (`website/api/`), with its tests in `website/tests/`.

Each language stays in its own tree, and the launcher's Rust crates never depend on the website. Never use Python for tooling or scripts.

Target platforms: **Windows, macOS, and Linux** (desktop only). This project does **not** target Android or iOS — do not factor mobile into analysis, recommendations, or dependency choices.

Build & tooling: tasks are orchestrated through a **`justfile`** (run recipes with
`just <recipe>`), and builds run in **Docker** for reproducible, cross-platform output. Prefer `just` recipes and the Docker-based build over ad-hoc commands. Formatting is enforced via `rustfmt.toml`.

Notes for iced:

- Elm architecture: state lives in the model; all mutation flows through `Message`s handled in `update()`; `view()` renders from the model
- Never block the UI thread — long-running work (downloads, IO, hashing, launching the game) belongs in async `Task`s or on background threads that report results back via messages
- Use `Subscription`s for ongoing side effects (timers, process output, file watching)
- Keep `view()` cheap and side-effect free — it runs on every redraw
- Prefer batching/`if let` message handling patterns consistent with existing code; do not introduce new UI frameworks alongside iced

## Core Principle

Every change has consequences. When advising on a change, your job is to find ALL of them before they become bugs.

## Analysis Protocol

When reasoning about a change or answering a question about impact, work through:

1. **Dependency Mapping**: Search the entire project for every file, function, type, trait, interface, and module that references the code in question. Use grep, ripgrep, or file-search tools aggressively. Do NOT rely on memory or assumptions.

2. **Impact Classification**: For each dependent, classify the impact:
    - **Direct**: Code that calls, imports, or implements the interface
    - **Indirect**: Code that depends on behavior or side effects (event ordering, state mutations, timing)
    - **Cross-platform**: Platform-specific code paths that may need parallel updates (Windows/macOS/Linux variants)

3. **Side Effect Analysis**: Explicitly enumerate:
    - Type signature changes and their propagation across workspace crates
    - Behavioral changes (return values, error conditions, timing)
    - State management impacts (shared state, caches, persistence)
    - Threading/concurrency implications (race conditions, deadlocks, blocking the iced UI thread)
    - Performance implications (allocation patterns, hot paths, UI thread blocking)
    - Platform-specific behavior differences
    - Serialization/deserialization compatibility (config files, network, cached data)

## Cross-Platform Considerations

- Check for platform-conditional compilation (`#[cfg(target_os = "...")]`,
  platform-specific modules such as `windows.rs`/`macos.rs`/`linux.rs`)
- Consider file path separators, line endings, and OS-specific APIs (config dirs, process launching, window/titlebar behavior, GPU drivers)
- Consider screen density, input methods, and per-OS UI conventions — iced abstracts the widgets, but custom widgets, windowing, and platform integration code may need per-OS paths
- Remember the supported set is **desktop only**: Windows, macOS, Linux. Never introduce or assume mobile targets

## Performance Mindset

- Flag allocations introduced in hot paths without justification
- Prefer zero-copy and borrowing over cloning
- Heavy work belongs on background threads, not the UI thread
- Recommend profiling before and after performance-critical changes

## Communication Style

- Present dependency analysis first: what you found, what is affected, and the plan
- If you discover risks that cannot be fully mitigated, explicitly flag them
- If a question is too ambiguous to answer confidently, ask for clarification rather than guessing

Without it, a menu still open beside one that just finished its close fade draws in the closed menu's slot. `MenuOverlay` does this in `finish_close` (`menu.rs`), as iced's own `tooltip.rs` does.

Wrap a hoverable card or row in `HoverTrack` rather than `on_enter`/`on_exit`. Do not clear a page's hover on other messages: a scroll tick would shrink the card under the pointer, and a card that scrolls away corrects itself on the next event (the next enter overrides it, or its own exit fires when it is built again). Panels that must close after an action set `open` false from the root. `PanelOverlay::overlay` forwards the content's own overlays, so a hint on a panel button shows.

A launch that needs one waits in `Games` (`wait_for_session`) while a single refresh runs (`start_refresh`), and `session_refreshed` applies the result. A refresh token is spent once, so `prepare` must never refresh.

The face shows first from `appearance_cache.rs` (`<config>/appearance/<uuid>/`).

Results are remembered in `mod_checks` and kept in the `mod_update_checks` table (migration 0019) through `mod_check_saves`; the Mods tab shows them at once (`show_kept_check`) and checks again only after `MOD_CHECK_TTL`. - Build profiles: `release` is the shipped build (fat LTO, one codegen unit), and `profiling` inherits it. `aurora_leaf` compiles at opt-level 0 in both: it is generated icon code (a `by_name` match per Iconify set), and optimising it was 605 of a 689 s release build. - Performance: `just perf` runs the debug build with the `perf` feature (F3 overlay, a once-a-second report in the console and `perf.log`, and `trace-*.json` for Perfetto, both in the config folder's `logs/`). `just profile` does the same on a release-speed build with symbols, for `perf record` or `samply`. Timed scopes are `perf::scope(name)` and counts are `perf::count`; both are no-ops without the feature. The file logs are written by a background thread (`logging.rs`), so a slow disk or console does not stall rendering. Keep message timings named by `perf::message_kind`, which must not use `Debug`.

Its atlas and parsed-tree caches also evict anything not drawn since the last allocation (`vector.rs` and `raster.rs` `trim`), so art that scrolls out of the virtualised list is rasterised again when it returns. Check `perf` `svg rasters/s` before adding any new scaled or scrolled SVG.

Pausing aborts the install with `keep_folder` set, and the `.installing` marker lets the resume take the folder over. `sweep_partial_installs` removes marked folders that have no row, once at startup. A card's photo is therefore drawn one radius taller with a symmetric radius and cut to its box (`discover/card.rs::Corners::bleed`). On hosts whose `libz.so.1` is zlib-ng (CachyOS, Arch with zlib-ng-compat), Mojang's runtimes fail Forge 1.18.2 and 1.20.1 with "invalid outputs", while the system OpenJDK (bundled zlib) passes. `install/loader.rs::run` retries once on a system Java at least as new as the game's. - Pins are `app/world_pins.rs` (root `world_pins`, table `world_pins`, migration 0009). `delete_instance` clears them by hand because the schema has no foreign keys. The instance tab reads them at view time; the Worlds page keeps a copy for its Pinned chip.
- A `Popover` trigger must be a plain element, not a `TextButton`: the button captures the press first, so the popover never sees it. `pages/worlds/header.rs::face` draws the header buttons as boxes for this reason.
- World art: `WorldFile.icon` is drawn at 2× with `FilterMethod::Nearest`, and `WorldFile.backdrop` is a blurred copy of the 64px icon (`files::decode_world_art`). `WorldFile.backed_up` is true when `backups/<world>-<YYYY-MM-DD_HH.MM.SS>.zip` exists (`files/backups.rs::is_backup_of`).
- Worlds backups: `files/backups.rs` (`BackupFile`, `parse`) reads each `backups/` zip from its name, and `Scan::read` (`pages/worlds/scan.rs`) reads the saves and backups in one blocking pass. The Backups chip (`WorldFilter::Backups`) lists them as rows in `list.rs::backups`, windowed like the table. It hides the sort and view controls, and no world passes it. Table rows show BACKED UP as the cards do (`world_card::backed_up_badge`). Restore imports the zip as a new save named after its folder, and never over one: `world_archive::restore` reserves the folder with `create_dir`, so restores that run at once take different names.
- Launch settings: `app/launch_settings.rs` holds `LaunchDefaults` (the global defaults, in `preferences.json` under `instance_defaults`) and `InstanceSettings` (an `Option` per launch field on `Instance.settings`, stored as JSON in `instances.settings`). `None` inherits. `resolve` merges the two into the `LaunchSettings` a launch reads in `games.rs::start_preparing` (`Target.settings`).
- Instance edits: the Settings tab emits `settings::Message::Edit`, which the root intercepts (`instances.rs::edit_instance`), applies to the page's copy, and saves with `Database::save_instance` through `writes::KeyedWriter` (one write in flight per instance, the newest snapshot follows). Banners and icons are written under a new name in `.lodestone/`, because iced's `Handle::from_path` caches by path.
- Settings scroll-spy (`pages/instance/settings/nav.rs`): sections are measured with a custom `Operation` over container ids. The scrollable's own id is not a container, so the offsets are measured from the inner column (`nav::column_id`), and the active section is the last whose top is within 40px of the scroll offset.
- The launch rows in `components/launch_rows.rs` are shared by the instance tab and the global Settings page (`pages/settings/mod.rs`). The rows emit `LaunchChange`, and the owner applies it to the instance or to the defaults.
- The global Settings page is `pages/settings/`: `mod.rs` holds the state, header and routing, `draft.rs` the saved and edited copies, and each tab has its own file. The sidebar gear is `NavGroup::Bottom` index 0, which `update.rs` routes to `Page::Settings`. Page titles use `h2!` (28px); `display!` is 72px.
- The Privacy switches (`SettingsValues.privacy`) are stored only. The tab marks each card "Not enforced yet", and no code reads them yet.
- Clear local data (`app/local_data.rs`) empties the sign-ins by saving an empty store through `save_credentials`, not by deleting `credentials.json`, so a write already in flight cannot land after it. `Preferences::remove` deletes `preferences.json`, and `Settings::replace_saved` resets the page's draft.
- The global Settings page is one scrolling column of six sections, each anchored by `Tab::anchor_id`. Its sidebar uses the generic `components/scroll_spy.rs` (`measure`, `active`, `scroll_to`) through `pages/settings/nav.rs`. The instance page keeps its own copy in `pages/instance/settings/nav.rs`.
- A shader's `update` sees `cursor.position()` in its scrollable's content coordinates, but `CursorMoved` in window coordinates. Mixing the two made the skin viewer's first drag jump to its pitch limit. `accounts/viewer.rs` (`Turn`) therefore measures a drag only from `CursorMoved` positions.
- Import Instance is `app/import/`. `dialog/` draws the modal, `prepare.rs` reads a source (a modpack file, a CurseForge page, or a `.lodestone` backup) into the `InstallRequest` that queues it, and `record.rs` with the `imports` table (migration 0011) keeps the recent list. Reads run on the blocking pool. The drop subscription exists only while the dialog is open.
- A `.lodestone` backup installs through `install/package.rs`, which the portable launcher shares. Its bundled files lay over the instance by `Origin::Package`. `install/pack.rs` builds a modpack's request for both Discover and Import.
- `boot.rs` sets `drag_and_drop: true` on Windows (iced's default). Without it Explorer drops never reach the Import dialog.
- The From launcher tab reads other launchers from `app/import/launcher/`, one module per layout. A launcher is looked for in its saved folder (`Preferences::launcher_folders`), its default folders (`roots.rs`), then the install folder its Windows uninstall entry names (`registry.rs`). Modrinth's `app.db` is opened read only, from inside a blocking task. `install/copy.rs` skips the launchers' shared downloads and credential files (`launcher_*`), and follows file links but not folder links.
- Rail tooltips: `NavRail` draws every icon itself, so `NavItem::labelled` gives a slot its tooltip, and `NavRail::overlay` draws it as a `BubbleOverlay` beside the slot. A sidebar tooltip is `hint::at(control, text, Position::Right)`. iced's draw asks `overlay()` again but reuses the layout the last update stored (`iced_runtime` `user_interface.rs`), so the bubble's tree lives in the rail's `State` (`bubble`), where its text is still laid out when it draws. Any custom overlay that draws text needs the same. A hover change requests a redraw, so the bubble appears on the next frame.
- News (`app/news/`): piston-mc's `news` and `java-patch-notes` types are read one entry at a time (`feed.rs`), so a new category or a missing field skips that entry rather than the feed. Patch-note HTML goes through `news/markdown.rs`, which keeps headings, lists, links, tables and entities; `pages/resource/readme.rs::to_markdown` drops headings and link targets, so it is only for project readmes.
- Servers: the Server List Ping, VarInt framing, chat text and LAN announcements live in `crates/server` (`lodestone_server`), which has no GUI code. The LAN socket binds 224.0.2.60:4445 with port reuse, and the LAN and ping clocks run only while the Servers page is open.
- Quick play is one target, `launch::prepare::QuickPlay` (a world, or a server). `join_arguments` writes `--quickPlayMultiplayer host:port` for 1.20+ and `--server`/`--port` for older versions.
- Notifications (`app/notifications/`): each row has a `key` UNIQUE, so repeatable events (crashes, installs, exports) carry a millisecond suffix from `event_key`, while updates use a stable key (launcher tag, pack version, mod count) so each is recorded once. Text is built at display time from `kind`, `subject` and `detail`, so it follows the language.
- Update checks (`notifications/checks.rs`) run when the library loads and then every six hours. An instance with no `source_version` takes the newest release as its baseline and raises nothing.
- Launcher updates are `app/updater/`: `mod.rs` holds the state, `target.rs` how this copy takes an update, and `tasks.rs` the download and the placing. `lodestone_updater` (`crates/updater`) does the GitHub check (with ETag), the checked download and the Unix placement. `Target::detect` runs once at boot: an installed Windows build runs the setup, a Linux build in a writable folder replaces its executable, a macOS app in a writable folder replaces its bundle, and any other copy only opens the release page. The download runs in the background when Auto-update Lodestone is on. The install starts only from the update button or the changelog's Update, and `busy` asks first while a game, download, install or export runs. Settings shows the switch only where a copy can install.
- Log filters: every log layer goes through `logging.rs::level_filter`, which holds `QUIET_TARGETS` (iced_winit at WARN; wgpu_core, wgpu_hal, naga, calloop, h2, hyper_util, inotify at INFO). iced_winit prints the window settings with `{:#?}` at INFO, the 512px icon's pixels included: a million lines formatted on the main thread before the window opened (over a second). A new chatty crate goes in that list. At launch the last run's logs are moved into `.tmp/` (`Take::Move`), not copied.
- Logs: `logging.rs` writes `logs/` in the config folder (`paths::logs_dir()`, re-exported from the lib). `main` calls `lodestone_launcher::prepare()` before `setup_logging()`, so a portable launcher's roots exist before its logs open. `prepare` runs before any subscriber, so its failures go to stderr.
- Data folder: `Preferences.data_folder` (top level of `preferences.json`, in the config folder) is the folder chosen on the General tab. Boot resolves it with `paths::resolve_data_root`. `app/data_folder.rs` moves each top-level entry of the root (a rename, or a copy then a removal across drives) and puts the moved entries back when one fails. It saves the choice only after the data lands, and `local_data` keeps the choice when it clears the settings. A move is refused while a game runs or a download, install or export has not ended, and `data_move` covers the window while it runs. A portable launcher's folder cannot move (`paths::is_portable`). Known gap: a crash mid-move leaves the data split between the two folders, since there is no journal.
- Mods tab: the Updates chip sets `ModFilter.updates_only`, and a mod with a newer release shows an Update button that sends the existing `Action::Update` menu message, so the install path is the menu's.
- Mods dependents: `ModFile.id` and `ModFile.dependencies` come from each jar's own metadata in `files/mods.rs::scan`, so no platform is asked. `Row.library` is set when another jar in the folder names the row's id as Required, Optional, Recommended or Suggested (`DependentKind::of`), and only a library offers `Action::Dependents`. `dependents_of` lists those jars, switched-off ones included. `State::set_mods` is the only place that recomputes the flag, so a change to the folder's jars must reach it through a rescan.
- Platform chips: `components/platform_logo.rs` (`chip`) draws a platform's mark alone in the pill the Discover cards use (`pill`). A mod's chip reads `Row.source` (`mod_sources`). A pack's reads `added_content` rows with an empty scope (`packs::State::set_sources`). A pack copied from a shared download records that download's platform there too (`Database::record_shared_origin`, called from `instance_packs.rs`), so Discover shows it as added. A modpack's packs are identified by hash on Modrinth with its mods (`mod_sources::modrinth_records`): the ones its `files` name, and the ones its overrides bundle, read from the archive (`install/pack.rs::bundled_packs`), for either platform. A `.lodestone` package's linked packs come from its manifest (`install/package.rs`). The install writes them after its row (`install/mod.rs`). A bundled pack is tried on the modpack's own platform first and the other second: Modrinth by its hash, CurseForge by its fingerprint (`platforms/src/fingerprint.rs`: MurmurHash2, seed 1, over the bytes without tab, line feed, carriage return and space) through `Platform::<CurseForge>::fingerprint_match`. The CurseForge step needs the build's key, and an unparsable answer logs a warning and names nothing. CurseForge manifests list only mods, by id, so a pack's CurseForge record comes only from its bytes.
- Servers from `servers.dat`: `pages/instance/files/servers.rs` reads each instance's file (NBT, gzipped or not) into `ServerFile`, and this code never writes it. `InstanceFiles.servers` and the watch's `Change::Servers` keep the instance Worlds tab's Servers section live, and Join launches that instance on the server. The Servers page merges every instance's list (`pages/servers/scan.rs`) with the launcher's `servers` table in `pages/servers/listed.rs`: one entry per address, with the launcher's name and address when it saved the server. A server only a list holds saves as a favorite from its star or menu. Games announced on the local network (`State::heard`, from `lodestone_server::lan`) join the same All list as `announced` rows, pinged like the rest. A game no list or save holds is not `known`, so the Join dialog and the instance Worlds tab leave it out.
- The resource page's back step returns to the instance whose Mods tab opened it. `ResourcePage::origin` is set by `open_from_mods_tab` (`mod_actions/mod.rs`), which `open_mod_resource` and `open_dependency` call. `resource.rs::open_resource_from_instance` also points the Discover page's target at that instance, so the page's selector and its releases' actions read it, and the page filters to the instance's Minecraft version once the releases load. A resource page names the project by its details once they load (`ResourcePage::name`), because a CurseForge modpack's mod records take the jar's file stem as their name. `resource.rs::back_to_instance` goes back by history when the instance is the page before, and otherwise opens the instance on its Content tab. Every other opener passes `None`, and the back step still goes to Discover.
- Chips in a row go through `components/chip.rs::chip_row`, which wraps. A plain `row` of chips squeezes its last chip's label out of the chip's outline once the row runs out of width, which is how the resource page's Tags section overflowed.
- CurseForge descriptions are HTML, and `components/html/` draws them. iced's markdown drops raw HTML, and an inline image there takes the text before it in its paragraph as alt text. `html::parse` runs `tokens` (tags and text, with `script` and `style` content skipped), then `tree` (HTML's recovery, at most 64 deep), then `blocks` (at most 8 nested containers), and `html::view` draws the `Document`. The resource page parses once on `Message::Details` into `ResourcePage::description`. `pages/resource/description.rs::resolve` joins CurseForge paths onto `https://www.curseforge.com` and unwraps `/linkout?remoteUrl=`, whose target is encoded twice. Only `http`/`https` addresses come out.
- In a description, `div.spoiler` and `details` start closed. `Message::Spoiler` toggles one, and `Document::pictures` lists only what a reader can see, so a closed spoiler's pictures load when it opens (at most 40, in reading order). An author's colour is drawn only at 3:1 contrast against `--bg-2` (`css::readable`, checked at view time). Author sizes scale from 16px to the page's 14px, within 10 to 36px. Italics draw upright, since no italic Inter is bundled; Modrinth readmes do the same.
